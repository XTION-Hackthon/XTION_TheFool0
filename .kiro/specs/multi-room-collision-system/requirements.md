# 需求文档：多房间碰撞系统

## 简介

多房间碰撞系统是一个前端功能，使用户能够在多个不同的房间内进行交互，具有复杂的空间管理能力。系统支持主大厅（MainHall）用于向所有用户广播，独立的私聊房间用于一对一或小组交互（每个房间最多2个bot），并实现物理碰撞检测，包括墙体碰撞和bot之间的交互。系统包括容量管理以防止过度拥挤，以及供管理员定义房间边界、墙体和容量限制的地图编辑器。

## 术语表

- **主大厅（MainHall）**: 系统中的主要广播房间，所有用户首次进入时的默认位置，支持无限数量的 bot 同时在线，用于全局消息广播和交互
- **私聊房间（Private_Room）**: 独立于主大厅的房间，用于两个 bot 之间的私密交互，最多容纳 2 个 bot，满员时自动关闭，新用户无法进入
- **Bot（机器人）**: 系统中的自主代理或用户控制的实体，可在房间内移动、与其他 bot 交互、发送消息
- **房间（Room）**: 游戏世界中的一个独立空间单位，包含主大厅和多个私聊房间，每个房间有独立的 bot 列表、墙体配置和容量限制
- **房间容量（Room_Capacity）**: 房间内允许的最大 bot 数量，主大厅无限制，私聊房间固定为 2
- **碰撞检测（Collision_Detection）**: 系统检测两个实体（bot 或 bot 与墙体）占据同一空间的能力，用于防止穿透和确保物理真实性
- **墙体（Wall）**: 房间内的物理屏障，bot 无法穿过，需要绕行，由位置、尺寸和方向定义
- **移动验证（Movement_Validation）**: 在 bot 移动前检查目标位置是否有效（无其他 bot、无墙体）的过程，验证失败则阻止移动
- **碰撞箱（Collision_Box）**: 围绕 bot 的空间边界，用于碰撞检测，不同 bot 类型可有不同尺寸
- **地图编辑器（Map_Editor）**: 供管理员使用的可视化工具，用于定义房间布局、放置墙体、设置容量限制和出生点
- **房间边界（Room_Boundary）**: 房间的空间限制范围，定义了房间的有效活动区域
- **位置（Position）**: bot 在房间内的精确 2D 坐标 (x, y)
- **目标位置（Target_Position）**: bot 打算移动到的位置
- **出生点（Spawn_Point）**: 新 bot 进入房间时的初始位置，主大厅有多个分散的出生点以避免碰撞
- **房间状态（Room_State）**: 房间的当前状态信息，包括在线 bot 列表、容量使用情况、墙体配置等
- **房间切换（Room_Transition）**: bot 从一个房间移动到另一个房间的过程，需要保留 bot 状态并更新位置
- **空间索引（Spatial_Index）**: 用于高效查询附近 bot 的数据结构，支持快速碰撞检测和范围查询
- **碰撞错误（Collision_Error）**: 当 bot 移动被阻止时返回的错误信息，包含碰撞原因（bot 或墙体）和位置信息
- **房间配置（Room_Configuration）**: 房间的完整定义，包括边界、墙体列表、容量限制、出生点列表等，可持久化存储

## 需求

### 需求1：多房间架构

**用户故事：** 作为一个用户，我想在不同的房间内交互，这样我可以进行广播对话和私密交互。

#### 验收标准

1. 系统应维护一个始终对所有用户可用的主大厅房间
2. 系统应支持创建独立于主大厅的私聊房间
3. 当用户加入系统时，系统应默认将其放在主大厅
4. 当用户首次进入主大厅时，系统应将其放在随机的出生点，而不是所有用户都在同一位置
5. 当用户发起私聊时，系统应创建或加入现有的私聊房间
6. 当用户在私聊房间时，系统应防止主大厅消息出现在该房间的聊天中
7. 当用户离开私聊房间时，系统应将其返回到主大厅

### 需求2：房间容量管理

**用户故事：** 作为系统管理员，我想强制执行房间容量限制，这样私聊房间就不会过度拥挤。

#### 验收标准

1. 系统应对每个私聊房间强制执行最多2个bot的最大容量
2. 当私聊房间达到最大容量时，系统应防止新用户进入该房间
3. 当用户尝试加入满员的私聊房间时，系统应显示错误消息，指示房间已满
4. 当bot离开私聊房间时，系统应立即使该房间对新用户可用
5. 系统应允许主大厅容纳无限数量的用户
6. 显示可用房间时，系统应指示哪些房间已满，哪些有可用位置

### 需求3：移动验证

**用户故事：** 作为一个bot，我想在移动前验证移动是否有效，这样我就不会与其他bot碰撞。

#### 验收标准

1. 当bot尝试移动到目标位置时，系统应检查是否有其他bot占据该位置
2. 如果另一个bot占据目标位置，系统应阻止移动并返回碰撞错误
3. 如果目标位置未被占据，系统应允许移动继续进行
4. 当bot移动时，系统应更新其在房间空间索引中的位置
5. 系统应在更新bot在数据库中的位置之前验证移动请求

### 需求4：墙体碰撞系统

**用户故事：** 作为一个用户，我想让bot尊重物理墙体，这样游戏世界感觉真实且可导航。

#### 验收标准

1. 当bot尝试移动到被墙体占据的位置时，系统应阻止移动
2. 当bot尝试穿过墙体时，系统应阻止移动并要求bot绕过它
3. 系统应为每个房间维护一个墙体地图，定义所有墙体的位置和尺寸
4. 当bot移动时，系统应检查与当前房间中所有墙体的碰撞
5. 如果移动会导致墙体碰撞，系统应返回碰撞错误及墙体位置
6. 系统应支持各种大小和方向的墙体

### 需求5：Bot碰撞检测

**用户故事：** 作为一个bot，我想检测与其他bot的碰撞，这样我可以适当地响应接近。

#### 验收标准

1. 当两个bot的碰撞箱重叠时，系统应检测到碰撞
2. 当检测到碰撞时，系统应通知两个bot发生了碰撞事件
3. 系统应为每个bot维护具有定义尺寸的碰撞箱
4. 当bot移动时，系统应检查其碰撞箱与房间中所有其他bot的碰撞
5. 系统应支持不同bot类型的不同碰撞箱大小
6. 当bot离开房间时，系统应从房间的碰撞检测系统中移除其碰撞箱

### 需求6：地图编辑器

**用户故事：** 作为管理员，我想编辑房间布局，这样我可以定义房间边界、墙体和容量设置。

#### 验收标准

1. 地图编辑器应提供用于编辑房间布局的可视化界面
2. 当管理员使用地图编辑器时，系统应允许他们定义房间边界
3. 当管理员使用地图编辑器时，系统应允许他们放置和移除墙体
4. 当管理员使用地图编辑器时，系统应允许他们设置房间容量限制
5. 当管理员在地图编辑器中保存更改时，系统应将更改持久化到地图配置
6. 当地图编辑器加载房间时，系统应显示所有现有的墙体、边界和容量设置
7. 当管理员在地图编辑器中删除墙体时，系统应从房间的墙体地图中移除它
8. 地图编辑器应验证房间边界是否正确定义后才允许保存

### 需求7：房间状态持久化

**用户故事：** 作为系统管理员，我想房间配置持久化，这样房间布局能在系统重启后保存。

#### 验收标准

1. 当在地图编辑器中配置房间时，系统应将配置保存到持久存储
2. 当系统启动时，系统应从持久存储加载所有房间配置
3. 当房间配置更新时，系统应立即持久化更改
4. 系统应维护房间配置的版本历史以便恢复
5. 加载房间时，系统应验证所有墙体和边界是否正确定义

### 需求8：空间索引和性能

**用户故事：** 作为系统架构师，我想要高效的碰撞检测，这样系统可以扩展到许多bot。

#### 验收标准

1. 系统应使用空间索引来高效查询附近的bot
2. 检查碰撞时，系统应仅检查同一房间内的bot
3. 当bot移动时，系统应更新其在空间索引中的位置
4. 系统应支持查询给定区域内的所有bot
5. 当房间有许多bot时，系统应保持碰撞检测性能

### 需求9：房间切换

**用户故事：** 作为一个用户，我想平滑地在房间之间移动，这样我可以切换上下文而不丢失状态。

#### 验收标准

1. 当用户从一个房间移动到另一个房间时，系统应保留其bot状态
2. 当用户离开房间时，系统应从该房间的参与者列表中移除他们
3. 当用户加入房间时，系统应将他们添加到该房间的参与者列表
4. 当用户切换房间时，系统应将其位置更新到新房间的入口点
5. 当用户在私聊房间中且该房间变空时，系统应标记该房间以供清理

### 需求10：碰撞响应和恢复

**用户故事：** 作为一个bot，我想优雅地处理碰撞，这样我可以恢复并继续移动。

#### 验收标准

1. 当bot与墙体碰撞时，系统应提供墙体的位置和尺寸
2. 当bot与另一个bot碰撞时，系统应提供另一个bot的位置
3. 当检测到碰撞时，系统不应将bot移动到碰撞位置
4. 当bot收到碰撞错误时，系统应允许它尝试替代移动
5. 系统应提供足够的碰撞信息供bot绕过障碍物

### 需求11：出生点分配

**用户故事：** 作为一个新用户，我想在进入主大厅时出现在不同的位置，这样我不会与其他新用户在同一位置碰撞。

#### 验收标准

1. 系统应为主大厅定义多个出生点位置
2. 当新用户进入主大厅时，系统应从可用的出生点中随机选择一个
3. 系统应检查选定的出生点是否被其他bot占据
4. 如果出生点被占据，系统应选择另一个可用的出生点
5. 系统应确保新用户不会在出生时与现有bot碰撞
6. 出生点应分散在主大厅的不同区域，避免聚集
